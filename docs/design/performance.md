# 素材成本与常驻性能

状态：历史数字见[审查](../plan/baseline.md)；下列新预算是待维护者选择的提案，尚未达标或冻结。不能用“当前值加 10%”自动批准产品预算。

## 分开计算五类成本

1. 下载：程序、默认素材、可选扩展各自的压缩字节。
2. 安装：去重后的运行载荷；另外报告升级暂存与上一版本占用。
3. CPU 内存：清单/帧索引、压缩输入、解码工作区、当前/预取页、命中数据、字体/UI、客户端缓存。
4. GPU：素材纹理、surface、UI 图集与设备/驱动开销分别报告；不能把 WDDM 总计等同于自建纹理池。
5. 持续成本：解码、哈希、页上传、GPU 等待、轮廓计算/提交、present、唤醒和客户端查询频率。

包体大不必然等于运行驻留大；有界页池也不说明整体开销小。PNG 解包后依然是压缩文件，不能把下载 ZIP 压缩率误当成降低解码或 GPU 成本。

## 默认包与预算提案

先选普通桌宠用到的语义动作和质量档，再定完整扩展。建议将默认素材 **ZIP ≤150 MiB、安装 ≤200 MiB** 作为首轮工程目标；程序附件另报，总默认下载暂以 ≤200 MiB 为目标。依据是当前六动作约 128 MiB 可作为起点，但还需加入姿态/资源并重测，不能宣称直接满足最终默认包。

完整 320 包约 505 MiB 可保留为可选对照；是否公开提供、上限是否允许 600 MiB 由 D05 决定。720 参照约 1.88 GiB 不进入默认附件。若视觉要求无法在预算内实现，明确比较减少动作、降低尺寸/时长、换编码和提高预算，不静默减少帧率或改变原始时序。

| 指标 | 首轮目标提案 | 当前证据与处置 |
| --- | --- | --- |
| 启动至角色可交互 | p95 ≤2 s，至少 10 次，冷/热条件分开 | 既有首帧约 0.4–0.5 s 不能替代可交互计时 |
| 输入至可见反馈 | p95 ≤50 ms、p99 ≤100 ms | 目前缺完整记录；重点覆盖跨页、设置和吸边切换 |
| 按原 24/30 fps 播放 | 稳态漏呈现 <1%，单报最长卡顿与动作首帧 | 不能仅凭平均 FPS，通过丢帧赶时钟也要计数 |
| CPU 素材活跃缓冲 | ≤32 MiB；每个分配项可解释 | 保留有界设计，现行单页限制另见 v1 |
| GPU 素材池 | ≤64 MiB | surface/UI/驱动单报，不用总显存冒充池大小 |
| Windows 全进程 private bytes | 待机 ≤256 MiB；打开设置 ≤384 MiB | 这是优化目标，历史约 443/895 MiB 尚不满足；冻结前测归因与可行性 |
| 待机 CPU | 10 分钟平均 ≤单逻辑核 2%，同时报告 p95 与唤醒 | 分 CPU 型号，不把 0% 采样解释为零成本 |
| 隐藏 | 无动画解码/上传/present；无忙等；查询计入独立预算 | 当前隐藏短测无提交，但内存未完全回落 |
| 稳定性 | 2 小时、100 次动作/设置/显隐切换后无持续资源增长 | 要报告稳定后增量、峰值及句柄/线程；有缓存须说明上限 |

内存目标必须经一次有时间边界的归因实验后，选择“达标方案、接受较高档位、改 UI/渲染策略”之一。旧 550/1,100 MiB 只是历史验收阈值，不自动成为新产品预算；也不为追求未经论证的 256 MiB 无限重写。

Linux 后续报告 RSS/PSS 等当地可取得的进程指标，不能把它们与 Windows private bytes 按数值直接判高低。GPU 利用率和功耗按同机相对比较，不设跨驱动通用百分比门槛。

## 必做的最小实验

| 实验 | 固定项 / 改变量 | 输出与选型规则 |
| --- | --- | --- |
| E1 尺寸与分页 | 相同动作、时序、Release 二进制、窗口物理尺寸；320/480/720，分别使用合法分页 | 记录质量、包体、解码/上传/命中、帧和输入延迟；选满足可见质量的最低成本档 |
| E2 全量与默认 | 相同待机、尺寸/编码；六动作/语义默认/39 动作 | 分开清单启动成本与活跃页成本，确认全量增大是否只影响磁盘 |
| E3 设置额外开销 | 同包；角色单独→设置打开→关闭→隐藏→恢复，至少 20 次 | 设备、字体、图集、surface、private bytes/句柄分项；确认保留缓存还是泄漏 |
| E4 编码与复用 | 同质量和时间线；PNG 基线与一个最佳候选 | 只有质量合格且关键成本稳定改善才替换；v1 同时携带 PNG 的限制单报 |
| E5 客户端附加成本 | 禁用→手动刷新→选定后台频率→断连 | 单列 worker、CPU、I/O、网络与超时；客户端自身模型成本不归桌宠 |

Windows 面板前端对照沿用 E3 的同包与重复开关条件。分别采样只运行角色、打开临时浮层、打开功能中心或设置以及关闭后的状态。记录首次打开耗时、增量内存、CPU 唤醒、进程与句柄，另报附带运行时、字体和面板组件的发行体积。用相同中文输入、长列表及流式追加文本样本对照候选实现，测量结果用于 D27 选型。[面板验收场景](panels.md)

E1 先用待机、特效互动、30 fps 移动、共享探头四种代表场景；筛出一档后再测全部交付动作，不做尺寸×编码×全部配方的无界组合。一次实验最多两个优化候选，必须导出“选用 / 不采用 / 数据不足”的结论和后续动作。

理论估算用于筛选：RGBA 页字节 = 宽×高×4；每页帧数减少会提高相同时间线的换页频率；帧像素数随边长平方增长。但读盘缓存、透明比例、PNG 压缩率、命中碎片数量和驱动行为都影响实际结果，因此不拿理论比例当实测收益。

## 测量协议

固定构建源码快照/二进制哈希、features、锁文件、包清单哈希、全部实验参数、OS/GPU/驱动、DPI、窗口物理尺寸、电源模式及前后台负载。dirty 工作树必须同时留 diff/文件哈希，不能只写 commit。

筛选可短测并标注。正式稳定场景预热 2 分钟、采样 10 分钟、至少 3 轮；发布再完成两小时常驻。启动至少 10 次，区分文件缓存条件。记录墙钟和单调时钟口径、预期帧/实际帧、取消/隐藏区间；CPU 100% 表示占满一个逻辑核，包含自有子进程并分项。

输入计时同时覆盖软件事件到呈现提交与可获得的实际显示反馈，报告测量方法；不能把 `queue.submit` 时间直接命名为屏幕显示延迟。页准备区分读/校验/解码、等待、上传，轮廓区分扫描与 OS 提交。

已有入口：`scripts/validation/p1/measure-p1b-playback.py`、`scripts/validation/measure-process.ps1`、`scripts/validation/p2/check-modal-playback.py`、`check-peek-slide.py`。先复用并补缺失指标；重命名脚本时保留调用迁移说明，不为新阶段复制一套脚本。
